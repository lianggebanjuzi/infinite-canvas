# Infinite Canvas 1.0 — 卡片系统瘦身重构计划

> 用途：交给其他 AI 或开发者分阶段执行。
> 核心目标：卡片只负责“声明 + 展示 + 少量交互”，业务执行、数据流、历史记录和持久化由独立模块负责。
> 强制要求：渐进重构，不推倒重写；每个阶段都必须保持 PyCharm 运行 `main.py` 可启动。

---

## 一、项目现状

当前前端正式入口已经是 TypeScript，Python 后端继续负责 pywebview、文件、图片和 AI API。不要把 Python 后端迁移为 TypeScript。

### 1.1 卡片代码规模

| 文件 | 行数（约） | 主要问题 |
|---|---:|---|
| `drawing-board-card.ts` | 1378 | 工具、图层、视图、历史、渲染、输入和卡片外壳仍在同一文件 |
| `ai-draw-card.ts` | 931 | UI、配置、API、轮询、并发生成、输出分发混合 |
| `agent-card.ts` | 553 | UI、上游数据、模型配置、API 调用、结果渲染混合 |
| `base-card.ts` | 491 | DOM 外壳、拖拽、缩放、端口、选择、撤销接口、数据流混合 |
| `preview-card.ts` | 330 | 媒体展示、元数据、下载和全屏预览混合 |
| `compare-card.ts` | 295 | 数据接收与图像对比 UI 混合 |
| `image-input-card.ts` | 223 | 图片数据、遮罩、上传和展示混合 |
| `text-card.ts` | 121 | 体量合理，可作为目标参考 |

卡片相关 CSS 合计约 3400 行，多个文件重复定义按钮、输入框、工具栏、空状态、加载状态和缩略图样式。

### 1.2 当前主要结构性问题

1. 卡片类直接访问 `window.xxx` 全局对象。
2. 卡片类直接调用 API，并管理异步任务轮询。
3. 卡片类直接拼接大量 HTML 字符串并绑定事件。
4. 同一份数据同时存在于 DOM、卡片实例、`AppState` 和配置对象中。
5. `CardFactory` 使用 `switch` 注册卡片，新增类型需要修改核心文件。
6. `CardOptions` 包含所有卡片的可选字段，类型边界不清晰。
7. 图片输入、预览和 AI 结果展示存在重复能力。
8. AI 绘图与 Agent 都重复处理供应商、模型选择、上游文本和加载状态。
9. 序列化依赖每张卡片自行拼装，容易漏字段。
10. 重构时缺少自动化测试保护。

## 二、目标架构

卡片系统拆分为六类职责：

```text
CardDefinition  卡片声明：类型、标题、端口、默认尺寸、执行器
CardShell       通用外壳：拖拽、缩放、选择、端口、标题栏
CardView        内容视图：渲染、局部输入和事件
CardStore       状态存储：卡片数据，不保存 DOM 对象
CardExecutor    业务执行：AI、Agent、ComfyUI、视频等
CardSerializer  保存恢复：版本迁移与旧项目兼容
```

### 2.1 卡片类最终只允许承担

- 声明自身类型和端口。
- 创建对应 View。
- 读取和更新自身状态。
- 暴露输入和输出数据。
- 提供极少量生命周期钩子。

### 2.2 卡片类禁止承担

- 直接调用 `window.pywebview.api`。
- 自己轮询异步任务。
- 管理全局撤销栈。
- 修改其他卡片 DOM。
- 自己遍历连接关系。
- 重复实现按钮、下拉框、加载态和错误态。
- 保存供应商列表等全局数据。

## 四、必须保持的兼容边界

以下约束在整个重构期间不可破坏：

1. `.icproj` 顶层格式版本保持 `2.0`。
2. 旧卡片类型名保持可识别：
   - `text`
   - `image`
   - `ai-image`
   - `drawing-board`
   - `preview`
   - `agent`
   - `compare`
3. 旧项目中的 `id / left / top / width / height / title / content / groupId / bypass` 必须继续恢复。
4. 不改变 Python `InfiniteCanvasAPI` 的现有公开方法名称。
5. 不删除 `gui/js` 回退代码，直到全部验收通过。
6. 不覆盖正式版 `dist/InfiniteCanvas.exe`。
7. 每个阶段完成后执行：

```text
npm run typecheck
npm run build
npm run verify:migration
```

8. PyCharm 运行 `main.py` 必须继续自动构建 TS 并打开桌面窗口。

## 五、分阶段执行计划

## 阶段 0：建立安全基线

### 工作

1. 为项目保存和恢复准备至少一个包含全部七类卡片的测试工程。
2. 记录当前序列化结果，作为兼容快照。
3. 建立最小测试框架，优先测试纯 TypeScript 逻辑。
4. 给下列行为建立测试清单：
   - 创建和删除卡片
   - 卡片移动和缩放
   - 连接和断开
   - 撤销和重做
   - 保存和恢复
   - AI 任务成功、失败、取消
   - 分组后保存和恢复

### 禁止

- 此阶段不要重写任何卡片。
- 不要修改项目格式。

### 验收

- 当前程序能启动。
- 基线项目保存后能重新打开。
- TS 构建通过。
- 形成一份基线检查记录。

---

## 阶段 1：统一核心类型

### 工作

1. 将 `src/types/cards.d.ts` 改为普通模块 `src/cards/core/card-types.ts`。
2. 定义明确类型：
   - `CardType`
   - `CardId`
   - `PortType`
   - `CardPortDefinition`
   - `CardDefinition`
   - `CardRuntimeState`
   - `CardSerializedDataV2`
   - `CardInputPayload`
   - `CardOutputPayload`
3. 使用可辨识联合类型替代巨型 `CardOptions`。
4. 允许旧数据经过适配器转换为新类型。

### 禁止

- 不要在此阶段改变 UI。
- 不要使用 `any` 逃避类型错误。
- 不要删除旧类型名，先提供兼容别名。

### 验收

- `card-factory.ts`、`snapshot.ts` 和七类卡片不再依赖宽泛的 `Record<string, unknown>` 传递核心数据。
- `npm run typecheck` 无错误。
- 打开旧项目结果不变。

---

## 阶段 2：建立 CardRegistry，移除工厂 switch

### 工作

1. 建立 `CardRegistry`。
2. 每类卡片通过定义对象注册。
3. `CardFactory.create()` 只负责：
   - 查询定义
   - 创建实例
   - 挂载外壳
   - 注册状态
4. 未知卡片类型返回可见的“缺失卡片”占位符，不得直接丢数据。

### 验收

- 新增测试卡片不需要修改 `CardFactory`。
- 七种旧类型都能创建和恢复。
- 未知类型不会导致整个项目打开失败。

---

## 阶段 3：提取 CardShell

### 工作

从 `base-card.ts` 提取以下通用行为：

- 标题栏
- 选中与多选
- 拖拽
- 缩放
- 输入输出端口
- 删除和上下文菜单入口
- 通用加载、错误、空状态容器

`BaseCard` 暂时保留为兼容适配层，内部委托给 `CardShell`。

### 目标

- `BaseCard` 控制在约 200 行以内。
- 卡片 View 不得自行实现拖拽和缩放。
- 卡片专属 CSS 不再重复定义通用按钮、输入框和状态样式。

### 验收

- 七类卡片外观和操作无明显变化。
- 拖拽、缩放、端口连线、选择、删除全部通过。
- 撤销移动仍可用。

---

## 阶段 4：提取 CardStore 与统一命令入口

### 工作

1. 状态以纯数据形式进入 `CardStore`。
2. DOM 只读取状态，不作为事实来源。
3. 更新卡片状态必须经过统一动作：
   - `updateCardState`
   - `moveCard`
   - `resizeCard`
   - `setCardContent`
4. 命令系统监听动作并生成撤销记录。
5. 画板局部历史可以保留，但必须通过统一接口暴露。

### 验收

- 修改标题、内容、位置和尺寸后可撤销/重做。
- 保存时不再遍历 DOM 获取核心状态。
- Store 中不得保存 HTMLElement、CanvasRenderingContext2D 或 SVG 元素。

---

## 阶段 5：提取执行器层

### 工作

先处理 `AIDrawCard` 和 `AgentCard`：

1. 创建统一 `CardExecutor` 接口。
2. 将 API 调用移至：
   - `ImageGenerationExecutor`
   - `AgentExecutor`
3. 将轮询、超时、取消和并发控制移至 `TaskPoller`。
4. 卡片只发出执行请求并展示执行状态。
5. 输出通过标准 `ExecutionResult` 返回，不直接操作下游卡片。
6. 统一供应商和模型选择数据源。

### 目标

- `ai-draw-card.ts` 降至约 300 行以内。
- `agent-card.ts` 降至约 250 行以内。
- 执行器可脱离 DOM 做单元测试。

### 验收

- AI 绘图成功、失败、取消和批量生成行为保持一致。
- Agent 文本和图片输入保持一致。
- 执行过程中删除卡片不会产生未处理异常。
- 下游数据仍能正确收到。

---

## 阶段 6：媒体卡片能力复用

### 原则

不要立刻删除 `image` 和 `preview` 类型。先共享内部能力，再决定是否合并用户界面。

### 工作

1. 提取 `MediaState`、`MediaView` 和 `MediaActions`。
2. 图片输入卡片使用“可编辑媒体模式”。
3. 预览卡片使用“只读结果模式”。
4. AI 输出展示复用同一 MediaView。
5. 下载、全屏、错误图、元数据展示使用共享组件。

### 验收

- 旧 `image` 和 `preview` 项目类型继续存在。
- 上传、遮罩、下载、全屏和 AI 结果展示全部正常。
- 两类卡片不再复制媒体渲染代码。

---

## 阶段 7：拆分画板卡片

画板是专业功能，不要与普通卡片合并，也不要一次性重写。

### 按原类逐个迁移

1. `DrawingBoardToolManager` → `features/drawing-board/tool-manager.ts`
2. `DrawingBoardLayerManager` → `layer-manager.ts`
3. `DrawingBoardViewController` → `view-controller.ts`
4. `DrawingBoardHistoryManager` → `history-manager.ts`
5. `DrawingBoardRenderer` → `renderer.ts`
6. `DrawingBoardInputHandler` → `input-handler.ts`
7. 最后只保留轻量 `DrawingBoardCard` 负责组合。

### 验收

- 每移动一个类就运行构建并手测。
- 图层、笔刷、橡皮、文字、缩放、平移、撤销、保存恢复全部保持一致。
- 最终 `drawing-board-card.ts` 控制在约 300 行以内。

---

## 阶段 8：统一数据流

### 工作

1. 合并或明确下列模块边界：
   - `CardEventBus`
   - `DataSource`
   - `ConnectionRules`
   - `PipelineEngine`
2. 只保留一个标准数据包结构。
3. 数据类型从仅有 `text | image` 扩展为可注册类型，但暂时不要增加新功能。
4. 卡片不得直接查找下游 DOM 或调用下游实例方法。
5. 处理循环依赖、取消和执行顺序。

### 验收

- 文本、图片在多级连接中传递正确。
- 循环连接不会造成无限执行。
- 分组执行行为保持一致。
- 数据流核心可以无 DOM 测试。

---

## 阶段 9：CSS 瘦身

### 工作

提取共享样式：

- `.card-control`
- `.card-button`
- `.card-toolbar`
- `.card-field`
- `.card-empty-state`
- `.card-loading-state`
- `.card-error-state`

卡片专属 CSS 只保留真正不同的布局和视觉。

### 禁止

- 不要全局格式化全部 CSS。
- 不要同时重新设计视觉风格。
- 不要为了减少行数使用难维护的超长选择器。

### 验收

- 所有主题下视觉正常。
- 通用按钮和表单样式只存在一份。
- 卡片专属 CSS 总量明显下降。

## 阶段 10：清理兼容层

只有前九阶段全部验收通过后才能执行：

1. 删除不再使用的 `window.xxx` 桥接。
2. 删除不再使用的 `declare const`。
3. 将旧 JS 移到明确的备份目录，不立即永久删除。
4. 更新开发文档和卡片开发模板。
5. 重新生成独立测试版 EXE。

### 最终验收

- 旧 `.icproj` 可打开。
- 新项目可保存并重新打开。
- 七类旧卡片全部可用。
- PyCharm 一键启动正常。
- TS 严格检查通过。
- 正式 EXE 未被覆盖。

## 六、建议保留和合并的卡片

### 继续保留为独立类型

- `text`：足够轻量。
- `drawing-board`：专业编辑器，职责特殊。
- `compare`：交互明确，适合独立存在。

### 共享能力但暂不删除旧类型

- `image` 与 `preview`：共享 MediaView。
- `ai-image` 与 `agent`：共享 AI Task 外壳、模型选择和执行状态。

### 未来新增功能的原则

ComfyUI、视频、ModelScope、RunningHub 不要直接各自新增一张巨型卡片。优先实现为：

```text
AI Task Card + Executor + Schema
```

只有交互结构确实完全不同，才创建新卡片类型。
