# 画布工作流现状分析

> 版本：基于 2026-08-18 代码基线 `0136548`
> 目的：把当前"文生图 / 图生图 / 反推 / 文本处理"如何构成工作流、如何连线、数据如何流动，完整客观地整理出来，供工作流设计琢磨。
> 阅读对象：产品与开发者本人。
> 代码索引见文末附录。

---

## 一、一句话现状

系统只有**两种节点**（图片生成、文本），靠**单向连线**构成流水线；连线只表达"上游图 → 下游参考图"这一种关系，而"文本 → 下游提示词"的关系**不走线、是旁路覆盖**。这是理解当前工作流最关键的一点。

---

## 二、节点模型

### 2.1 节点类型（只有 2 种）

| 类型 | 标签 | 做什么 | 产出 |
|---|---|---|---|
| `image-gen` | 图片生成 | 参考图 0~N + 提示词 → 生成图 | 图（写回自身 或 新建产出节点，见 §3） |
| `text-gen` | 文本 | 命令 + 文本模型 → 处理文本 | 文本（写回自身卡片） |

### 2.2 节点字段（影响工作流的）

```
FlowNode
  ├─ status    idle / run / done / stale / fail    五态状态机
  ├─ imageUrl  本节点输出图（卡片主视觉）★ 与 refImages 严格分离
  ├─ refImages 用户主动挂载的参考图（默认 []）
  ├─ parentId  引擎产出节点标记：本节点由谁生成（重跑顶掉旧产出用）
  ├─ trace     生成档案（prompt/model/比例/分辨率/参考图指纹/父节点）
  ├─ outputText / textHistory   text-gen 专属
  └─ params    按类型不同（见下）
```

### 2.3 各节点参数

**image-gen（StyleTransferParams）**

| 参数 | 取值 | 备注 |
|---|---|---|
| prompt | 文本 | **多重语义**：绘图时=生成提示词；反推模式=命令 |
| model | provider:model | 绘图模型 |
| aspectRatio | 3:4 / 1:1 / 16:9 / Auto 等 15 档 | |
| resolution | 1k / 2k / 4k | |
| count | 1~4 | 一次生成张数 |
| modelType | draw / text | **反推开关**：text=用文本模型看图反推 |
| textModel | provider:model | 反推时的文本模型 |

**text-gen（TextGenParams）**

| 参数 | 取值 | 备注 |
|---|---|---|
| instruction | 文本 | 命令（临时，发送后清空） |
| model | provider:model | 文本模型（chat 系） |

## 三、五种运行行为（核心！）

同一个 image-gen 节点，根据"有没有参考图、模型 chip 是什么"，运行后行为完全不同：

### 3.1 文生图（无参考图 + draw）

```
[image-gen] --count=1--> 第 1 张【写回自身】→ 节点本身变成那张图
             --count=N--> 第 1 张写回自身 + 第 2..N 张各建一个新 image-gen 产出节点（连右侧）
```

- 节点"自己是产物"：运行后自身 imageUrl 变成新图。
- 产出节点也是 image-gen，可继续编辑/反推/连线。

### 3.2 图生图（有参考图 + draw）

```
[image-gen] --每张--> 各建一个新 image-gen 产出节点（连右侧）
源节点：成功后旧 imageUrl 先入历史图库，再【清空】→ 节点变回"空生成器"
```

- 源节点永远不自己变成图，是纯"生成器"。
- 参考图 = 用户挂载 refImages ∪ 直接上游输出图（§4.2）。

### 3.3 文本反推（有图 + modelType='text'）

```
[image-gen] --反推--> 新建一个 text-gen 节点（标题「文本反推」），放在右侧
源节点：done；【不建连线】
```

- 反推结果节点与图片节点**没有连线**，它是游离的文本节点。
- 反推要求图必须是 `data:image` 内嵌格式（旧项目 http 图不支持）。

### 3.4 扩图（独立入口，不改变节点）

```
[image-gen] --扩图悬浮面板--> 前端合成白底底图 → banana 系模型补全
            → 新建 image-gen 产出节点（连右侧）
```

- 参数不持久化（首版不支持扩图重跑）。

### 3.5 文本处理（text-gen）

```
[text-gen] --命令--> chat_v2 处理当前文本 → 结果写回自身卡片（outputText）
成功后：覆盖【直接 image-gen 下游】的 prompt ★ + 下游全部标 stale
```

- text-gen **不建连线**地"隔空修改"直接下游 image-gen 的提示词。
- 这是文本流传递的唯一机制。

## 四、连线机制

### 4.1 连线规则（canConnect）

| 规则 | 说明 |
|---|---|
| 不能连自己 / 不能重复 | |
| 不能成环 | BFS 防环 |
| **text-gen 不能作为接收端（to）** | 文本节点前方不插步骤；但可以作 from 喂下游 image-gen |
| 加边 / 删边 / 插步骤 / 换图 | 下游及其全部子孙标 stale |

入口：卡片连接点 / 右键菜单（手动连线 P0 已实现）；模板默认连好。

### 4.2 参考图合并规则（getReferenceImages，唯一入口）

```
getReferenceImages(节点) =
    本节点 refImages（用户挂的，在前）
  ∪ 直接上游的 imageUrl（上游有输出图时；无输出图则回退展开上游的 refImages）
  （去重保序）
```

**关键事实：只取直接上游一层，不做 BFS 传播。**

```
A → B → C
C 只能看到 B 的输出图，看不到 A 的图。
A 的图要传给 C：要么手动给 C 挂 refImages，要么 B 不产生新图。
```

### 4.3 连线的真实语义

**线只表达"图片流"**：上游图 → 下游参考图。
**文本流不经过线**：text-gen 结果 → 旁路覆盖下游 image-gen 的 prompt。

> ★ 这意味着：**屏幕上看到的线 ≠ 实际的全部数据依赖**。文本对下游的影响是无形的。

## 五、运行语义

### 5.1 五态状态机

```
idle → run → done ──(上游变化)──→ stale → run → done
              └→ fail（失败保留旧图，红点显示原因）
```

### 5.2 可运行条件（canRun）

| 节点 | 条件 |
|---|---|
| image-gen（draw） | 提示词非空 + 已选绘图模型（**参考图 0~N 可选，无图也能跑**=文生图） |
| image-gen（反推） | 已选文本模型 + 命令 + 有图（自身 imageUrl 或第一张参考图） |
| text-gen | 已选文本模型 + 命令非空 |

### 5.3 重跑顶掉策略（removeChildren）

- 重跑前先清掉上次的"纯引擎产出"子节点；
- **锁定**的产出节点 → 保留 + 标 stale（不删）；
- **手动改造过**的产出节点 → 保留 + 标 stale（不删）；
- 图生图源节点旧图若被锁定 → 不清空（保留主视觉）。

### 5.4 分段执行

- 选中节点 → 底栏"运行选中"（多选可批量）；
- 跑一段看一段，上游变化下游自动标 stale，用户决定何时重跑。

## 六、交互入口一览

| 入口 | 位置 | 作用 |
|---|---|---|
| 指令面板 | 选中卡片贴下沿 | 参考图区 + 提示词 + 模型/比例/分辨率/张数 chip + 发送 |
| 底部胶囊 | 底栏 | 打开/保存/主题/设置 + 运行选中 + 对比(n) |
| 对比面板 | 多选后触发 | 2/4/8 宫格并排对比 |
| 右键菜单 | 卡片 | 新建/删除/连线/插步骤等 |
| 扩图悬浮面板 | 卡片悬浮 | 选比例 + 合成底图 + banana 补全 |
| 历史图库 | 左侧抽屉 | 跨会话生成历史（image/text 流水） |
| 资产库 | 左侧 | 采纳/锁定图资产（成图库） |
| 反推 | 指令面板模型 chip | 切到文本模型 → 输入命令 → 生成文本节点 |

## 七、后端能力边界

- `chat_v2`：文本 / 多模态（反推）统一入口；
- `generate_image_async` → `get_task_result`：异步 202 + 轮询；
- 模型格式：`gemini_native`（gemini / nano-banana / seedream）、`openai_image`（gpt-image）、`openai_chat`；
- 多供应商多 Key：`provider:key:model` 三段解析，每 key 独立模型组；
- 图片落盘：原图 + 缩略图（JPEG q85/1024px），大图按需 `load_local_image` 桥接。

## 八、数据流全景（两张通道并行）

```
【图片流——走线】
  上游.imageUrl ──线──▶ 下游 getReferenceImages（只取直接上游一层）
                      下游 buildOptions.referenceImages → 后端 img2img

【文本流——旁路，不走线】
  text-gen.outputText / 就地编辑 ──旁路覆盖──▶ 直接下游 image-gen.params.prompt
                                             └→ 下游标 stale

【反推——生成游离节点，不连线】
  图片 → 反推 → 新建 text-gen（无连线）→ 若要影响下游，需手动连出去
```

## 九、结构性张力观察（作者视角，供琢磨）

> 以下是我读代码后观察到的"奇怪感"来源，不一定对，只是列出来。

1. **同一个节点，两种人格**：文生图时节点"自己变成图"（产物型），图生图时节点"只是生成器"（操作型），且两者切换由"有没有参考图"这个隐性条件决定——用户点运行前无法从卡片上预判这次会怎样。

2. **线表达的 ≠ 实际依赖**：屏幕上只有图片流走线；文本对下游提示词的覆盖是无形的。连线图给不了"这个节点为什么变成这样"的完整解释。

3. **上游图只传一层**：A→B→C 链越长，C 越"失忆"。多级流水线需要手动重复挂参考图，违背"连线即传递"的直觉。

4. **text-gen 的位置尴尬**：它不能作为接收端（前面不能插步骤），结果却会隔空改下游 prompt；它的"输入"来自自身卡片文本而非上游图。文本流和图片流两套机制并存，心智负担大。

5. **反推入口藏在 image-gen 里**：modelType='text' 是图片节点上的一个开关，反推结果又是一个游离的 text-gen 节点，既不连线也不在流水线里。发现性和闭环都弱。

6. **产出节点会无限向右长**：每轮图生图/批量/扩图都新建产出节点，链条不断右移，没有折叠/分组/收纳机制，画布会越来越乱——"连线奇怪"很大程度是视觉乱象。

7. **提示词框语义随模式漂移**：同一个输入框，draw 模式是"生成提示词"，反推模式是"命令"，text-gen 是"命令"。模式切换靠小 chip，不醒目。
