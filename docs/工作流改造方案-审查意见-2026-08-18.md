## 二、需要修正的 3 处

1. **阶段 4"脏标记 BFS 到底"是误读**。现状 stale 传播早已全下游 BFS（`getAllDownstreams` 注释即"用于脏标记传播"）。真正的新工作是：a) 数据收集层（决策 3）；b) 分家后 gen 重跑顶掉"旧 image 产物"的策略适配。阶段 4 的描述应改为"验证 stale 全链传播 + 适配新节点类型"。
2. **阶段 4"新增运行整条链"改为"增强 runAll"**：`runAll` 已存在（拓扑 + 遇失败停止）。要做的是增加"一键重跑整条 stale 链"入口（底栏按钮 → 收集所有 stale → 拓扑 → 顺序跑），而非新造引擎。
3. **阶段 3 上传图的描述补一句现状**：现状拖图/文件选择已建 image-gen 带图节点，改造后仅是换成建 image 节点，交互入口（file-input + 画布拖放）不动。

## 三、方案遗漏的 7 个改造点（施工前必须补进计划）

1. **老反推态节点迁移**：旧项目里 `modelType='text'` + textModel 的 image-gen 节点，阶段 2 删开关后怎么读？建议 migrateNode：反推态节点 → 迁移为 text 节点（model 继承 textModel、指令留空、outputText 空），或保持 image 节点并提示"反推已移到文本节点"。**方案未提，必补。**

2. **文本节点"数据+操作"两职需声明为有意例外**：方案表格里 text 角色=数据+操作，与"图操分家"原则表面冲突。可接受（文本无"自身变产物"歧义），但文档应写明这是有意为之，否则施工者会困惑。

3. **扩图（outpaint）没进方案**：`runOutpaint` 现状是 image-gen 悬浮入口。分家后 image 节点不可运行，扩图入口放哪？建议：扩图归入 gen 节点的一种模式（连图 + outpaint 参数），image 节点右键提供"扩图"操作（点它自动建 gen 并预填）。

4. **trace 生成档案的归属要明确**：现状 trace 挂"文生图写回自身的源节点"。分家后产物是新的 image 节点——**trace 应挂 image 节点**（记录"这张图怎么来的"），gen 节点不带 trace。否则 action-bar 复现按钮（按 trace 显隐）、historyPersist 建 trace、资产库采纳元数据全会错位。

5. **compare-panel 依赖要改**：可对比节点判断 = `image-gen 且 imageUrl 非空`（`compare-panel.ts _comparable`）。分家后应为 **image 节点**。小改但必须列入清单，否则对比面板失效。

6. **removeChildren / 重跑顶掉适配**：现在按 parentId 清"纯引擎产出"子节点（锁定/手动改造的保留+标 stale）。分家后：gen 重跑 = 删旧 image 产物（parentId=gen）→ 建新。锁定保护反而更清晰：锁在 image 节点上，gen 重跑不碰锁定产物。**这是改造的加分项，方案可明说。**

7. **历史图库 / 资产库**：history.jsonl 的 image 行、ImageAssetRecord 均按"节点有图"工作。分家后所有产物都在 image 节点上，这些逻辑**基本不变**（只是节点类型换），但 migrateNode 后老记录 nodeId 指向的节点类型变了，建议阶段 3 顺带回归一次历史图库与资产库。

## 四、三个待定决策的建议

| 决策 | 建议 | 理由 |
|---|---|---|
| 1. 生成节点连多个文本上游时 prompt 如何合并 | **拼接**（按连线顺序/上游 id 序），gen 面板保留手动改写入口 | 简单、可预期、不丢信息；"取一个"太武断，"手动选"增加交互成本 |
| 2. 生成节点是否显示产物预览 | **倾向：空壳操作卡**（只显示状态色/流光），产物图一律在右侧 image 节点；如怕"看不见上次出了啥"，可显示"最近一次产物缩略图"但标注产物在右侧 | 空壳才真正贯彻"图操分家"，视觉上数据/操作一眼可分；这是本次改造的灵魂，不建议妥协成"又变成半个数据节点" |
| 3. 数据是否沿线无限传播 | **只取直接上游，不穿透** | 分家后链是 数据→操作→数据→操作，操作节点的直接上游就是数据节点，**一层天然够用**；穿透会把 gen 的"多参考图"语义搞乱，徒增复杂度 |

## 五、迁移拆分具体建议（方案最大风险点，细化）

老 image-gen 节点的拆分规则，建议按"是否带图、是否有产出归属"四象限，**规则简单可预期**：

| 老节点形态 | 迁移结果 |
|---|---|
| 带 imageUrl + `parentId=null` + 有 prompt（手建的生成器，文生图写回过） | → **image 节点**（原图保留），gen 由用户按需从图拉出。不自动拆双节点，避免画布翻倍；"想改图 = 从图拉生成节点"正好借迁移教新交互 |
| 带 imageUrl + `parentId!=null`（引擎产出节点） | → 纯 **image 节点**（parentId 保留，供重跑顶掉/锁定逻辑用） |
| 带 imageUrl + `parentId=null` + 无 prompt（纯上传图） | → 纯 **image 节点** |
| 不带 imageUrl + 有 prompt（空生成器） | → **gen 节点**（参数全继承） |
| `modelType='text'` 反推态 | → **text 节点**（见三.1） |

迁移在 `persistence.ts migrateNode` 内完成（有 image-result 先例），version 升 3.5。**务必先在测试项目验证迁移，再碰真实数据**（方案已强调，认同）。

## 六、施工顺序微调建议

原方案阶段划分（地基→文本→图→清理→体验）合理，只补两点：

1. **阶段 2 的 canConnect 放开要连带定义 text 节点的输入语义**：text 节点可接收上游图（反推）与上游文（参考文本），建议明确"text 输入 = 上游图（走图片参数）+ 上游文本（拼进 user prompt）+ 用户命令"，避免阶段 2 做完留下模糊地带。
2. **阶段 3 与"批量变体对比"天然衔接**：分家后 count>1 会产出多个 image 节点，正好是批量对比的原料。若后续要做批量对比，阶段 3 的产出节点布局（现有 cursorY 避让逻辑）可直接复用。
