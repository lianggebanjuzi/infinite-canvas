## 一、项目现状

### 1.1 已完成（能力清单）

| 层 | 能力 | 说明 |
|---|---|---|
| 生成引擎 | 多供应商 / 多 Key / gpt-image / FluxPort | 每 key 独立模型组，三段解析 provider:key:model；FluxPort 异步 202+轮询真机出图成功 |
| 图片性能 | 原图落盘 + 缩略图渲染 | 4K 上百张不卡；大图按需 load_local_image 桥接 |

| 评估层 | 对比面板 2/4/8 宫格 / 复现按钮 / 成图库 / 资产库 | compare-panel + reproduce + asset-store |
| 节点模型 | 双卡：image-gen / text-gen | 注册式扩展；脏标记、分段执行、选中运行、锁定跳过 |
| 后端 | UnifiedAPIRouter 统一路由 / 供应商管理 | chat_v2 / generate_image_async / gemini_native / openai_image |

### 1.2 核心判断

**产品能力（生成）强于产品体验（组织与选择）**。生成链路已很完整，弱在"生成之后怎么选、怎么复用"——这是 08-18 所有讨论的起点。

## 二、背景：三个问题的由来

1. **产品路线**：原定剩余路线为 批量变体对比 → Agent → 模板固化；经分析重排为 批量变体 → 真实使用 → 模板固化 → Agent（Agent 搁置到最后）。
2. **工作流奇怪感**：用户反映"文生图/图生图/反推连线很奇怪"→ 产出《画布工作流现状分析》→ 定位 7 条结构性张力，根因是"三套数据传递机制并存 + 节点身兼图/操作两职"。
3. **参考项目启发**：用户发现 `basketikun/infinite-canvas` 的图库/资产库"分开"做得更好 → 团队调研产出《参考项目-图库资产库对比分析》→ 结论：参考项目强在"产品化"，本地强在"数据能力"。

## 三、已拍板决策（08-18）

### 决策 1：图操分家（节点模型主线改造）

- **问题**：image-gen 身兼"图（数据）+ 生成（操作）"两职；图片流走线、文本流旁路、反推游离三套机制并存 → 屏幕上的线 ≠ 实际依赖。
- **方案**（用户提出 v1，主理人审查通过）：
  - 节点收敛为三类：**image（纯数据图，不可运行）/ text（文本，可运行）/ gen（生成操作，永远吐新 image 节点）**
  - 文本走线：text 节点可接收上游图（反推归位），删除 image-gen 上的 modelType='text' 反推开关
  - 删旁路：删除"text 结果偷偷覆盖下游 prompt"逻辑
  - 一切走线：所有数据（图、文）显式走线，线 = 全部依赖真相
  - 一键重跑整条链：增强现有 runAll（已有拓扑排序），加"重跑 stale 链"入口
- **施工**：5 阶段（准备 → 统一取上游 → 文本走线 → 图操分家 → 清理+重跑 → 收纳体验），每阶段独立验证；里程碑 M1 文本连图反推 / M2 图操分家跑通示例链 / M3 改前面一键重跑整条链。
- **审查要点（已核实代码）**：
  - 脏标记传播现状已是全下游 BFS（getAllDownstreams），阶段 4 只需验证+适配，非新增
  - runAll + _topoSort 已存在，是增强而非新建
  - 遗漏点需补：老反推态节点迁移、扩图归属、trace 归属（应挂 image 节点）、compare-panel 可对比判断、removeChildren 顶掉适配、历史/资产回归
  - 待定决策建议：多文本 prompt 拼接；gen 空壳操作卡；数据不穿透只取直接上游
- **最大风险**：老 image-gen 节点迁移拆分（先测试项目验证再碰真实数据）。

### 决策 2：双库职责分清（历史图库 + 资产库都保留）

- **关键事实（已核实代码）**：
  - **历史图库是按项目存的**：`<项目名>.history.jsonl` 与 .icproj 同目录 → 换项目看不到旧项目历史
  - **资产库是全局跨项目的**：assets.json 全局存储，采纳记录 `projectName[]` 跨项目溯源 → 换项目还在
- **决策**（经用户两轮纠偏后拍板）：
  - **历史图库 = 项目内生成记忆**：图 + 提示词 + 参数 + 参考图（trace 已有），项目内浏览/搜索/拿出来
  - **资产库 = 跨项目常备资源**：采纳的图换项目可见可复用，必须保留（用户的直觉正确：历史跟项目走，资产跨项目）
  - 去重 / 锁定：**不折腾，保持现状零成本**（其价值是库索引主键与工作流保护，不是防丢；历史兜底图不丢，故不作为重点）
- **要补的缺口**：**资产条目配方持久化**——现在采纳时配方（prompt/model/比例/分辨率/参考图）只存内存、跨会话即丢，资产库里的图看不到提示词、无法复现。即参考项目调研的 **R2（AdoptMeta 持久化）**。

### 决策 3：借鉴取舍（参考项目 basketikun/infinite-canvas）

- **学（产品化）**：
  - R1 资产条目加 title/note/source 元数据 + 编辑（可选）
  - R2 资产配方持久化（采纳时 prompt/模型/参数/参考图随记录落盘）——**优先**
  - R3 历史按批次分组浏览（一次生成 N 张合并为一张批次卡，对症"选图慢"）——**优先**
  - R4 素材可外部上传入库（与图操分家后"上传=建 image 数据节点"同构）
  - R5 历史/资产入口语境分离（历史不自动弹、资产可全屏）
  - R6 素材 CRUD + 导出/导入
  - R8 点击插入 + 拖拽并存
- **留（数据能力，本地已优，不退化）**：指纹去重（hashRef 主键）、锁定保护（重跑不顶掉采纳图）、生成配方溯源（refHashes/seed）、磁盘原图文件
- **不抄**：二元素材模型（无去重/锁定，删了是退化）、浏览器 Blob 存储（破坏"拿到原图"交付刚需）、素材与历史彻底零关联（本地 trace/复现应保留加强）

## 四、待施工路线

```
① 资产增强（小改·可先行）  →  ② 图操分家（主线大改造）  →  ③ 批量变体对比  →  ④ 远期
```

| 步 | 内容 | 依赖 | 优先级 |
|---|---|---|---|
| ① 资产增强 | R2 资产配方持久化 + R3 历史批次分组（+R4 外部上传可选） | 无，独立可先行 | **现在做** |
| ② 图操分家 | 节点模型 5 阶段改造，image/text/gen 三类 | 无 | 主线 |
| ③ 批量变体对比 | count>1 产多个 image 节点 → 自动进对比面板 | 依赖 ② 的产出节点形态 | ② 后 |
| ④ 远期 | 真实使用积累（usage.log）→ 模板固化 → Agent | ③ 后 + 使用数据 | 长期 |

**关系**：①不依赖②、可立即施工且直接修复"跨项目看到图但看不到配方"的痛点；②是主线大改造（最大风险：迁移）；③在分家后自然长出（产出节点布局可复用）。

## 五、关键约束与已修正认知（防再踩）

1. **历史图库 = 项目级，资产库 = 全局级**——这是用户体感"资产库换项目还在"的真相；任何"合并/砍掉资产库"的方案都不成立。
2. **锁定/去重的正确定位**：不是"防丢"（历史兜底图不丢），而是"重跑顶掉机制下保护采纳图的工作流状态"与"资产索引唯一主键"。不作为优先增强项，保持现状。
3. **图操分家的地基事实**：脏标记传播已是全下游 BFS；拓扑运行引擎已存在；真正的缺口是数据收集层与分家后的顶掉适配。
