## 二、产品定义

### Product Goals（3 个正交目标）

1. **零丢失（数据安全）**：任何时刻——误关窗口、崩溃、切项目——都不丢工作；崩溃最多丢 60 秒，且项目文件永不半写损坏。对应功能：原子保存 + 自动保存 + 关闭保护 + 打开前 dirty 检查。
2. **可追溯（档案）**：每次 AI 生成都有一条持久化 trace，跨会话可查「每张图怎么来的」。对应功能：历史图库持久化。
3. **可回退（控制感）**：画布上的误操作（误删节点/误连线/误改参数）能一键撤销/重做，且与自动保存、快照共存不打架。对应功能：最小撤销/重做。

### User Stories

- **US-1（原子+自动保存）**：As 设计师，I want 我的项目改动被自动保存、且落盘不会写坏文件，so that 我随时关掉或崩溃，最多只丢一分钟的工作，且永远不会得到一个半截坏文件。
- **US-2（关闭保护）**：As 设计师，I want 在有未保存改动时关闭窗口会弹窗让我确认，so that 我不会因为手滑误关而丢掉一整段工作。
- **US-3（打开前 dirty 检查）**：As 设计师，I want 打开/切换项目前系统检测未保存改动并提醒我，so that 我不会用另一个项目覆盖掉当前还没保存的内容。
- **US-4（最小撤销/重做）**：As 设计师，I want 撤销/重做最近的画布操作（节点增删、连线增删、参数修改），so that 误操作能一键回退而不必手动重来。
- **US-5（历史图库持久化）**：As 设计师，I want 每次 AI 生成的档案（prompt/模型/比例/分辨率/参考图/时间/父节点）持久化到历史文件，so that 关掉软件重开后仍能查到每张图是怎么生成的。

## 三、技术规范

### Requirements Pool

> P0 = 本次必须（信任地基的验收路径）；P1 = 强烈建议，随 P0 一并或紧随；P2 = 可延后。

#### 功能 1 · 原子保存（P0）

| ID | 需求 | 优先级 |
|---|---|---|
| R1.1 | 后端落盘项目文件必须「先写同目录 `.tmp` 临时文件 → 写入并 flush 成功 → `os.replace` 原子替换目标文件」，全程在 Python 后端完成 | P0 |
| R1.2 | `os.replace` 失败时，原目标文件必须保持原样不动，返回错误；`.tmp` 在成功或失败后都清理 | P0 |
| R1.3 | 手动保存、另存为、首次保存（选路径）三条路径统一走同一原子落盘逻辑，不得有旁路直接 `open(w)` 覆盖 | P0 |
| R1.4 | 崩溃后遗留的 `.tmp` 在启动时清理（不误当项目文件） | P1 |
| R1.5 | 保留最近 N 份历史版本备份（如 `*.bak` 或 `snapshots/`），崩溃后可手动回退到上一版 | P2 |

#### 功能 2 · 自动保存（P0）

| ID | 需求 | 优先级 |
|---|---|---|
| R2.1 | 60 秒定时自动保存，仅在 `dirty === true` 时触发；无改动不写盘 | P0 |
| R2.2 | 窗口失焦（blur）时，若 `dirty === true` 触发保存 | P0 |
| R2.3 | 自动保存静默进行：不弹对话框、不打断操作；成功仅更新顶栏保存状态指示（不逐次弹 toast） | P0 |
| R2.4 | 自动保存与手动保存互斥：保存进行中再触发则串行排队或合并，禁止同时写同一文件 | P0 |
| R2.5 | 无路径的新项目：自动保存不静默失败，行为由架构师在设计中明确（写临时恢复文件 / 跳过并保持 dirty，见 Open Questions） | P0 |
| R2.6 | 自动保存间隔可配置（设置项，默认 60 秒） | P2 |

#### 功能 3 · 关闭保护（P0）

| ID | 需求 | 优先级 |
|---|---|---|
| R3.1 | pywebview 窗口关闭事件被拦截：`dirty === true` 时弹确认框（三选一：保存并关闭 / 不保存 / 取消） | P0 |
| R3.2 | 选「保存并关闭」：完成保存（成功）后才真正关闭；保存失败则回到应用、不关闭、提示原因 | P0 |
| R3.3 | `dirty === false` 时直接关闭，不弹窗 | P0 |
| R3.4 | 运行中（有节点在生成）的关闭行为由架构师明确：提示「有任务在跑，关闭会中断」或先等待/取消（见 Open Questions） | P1 |

#### 功能 4 · 打开项目前检查 dirty（P0）

| ID | 需求 | 优先级 |
|---|---|---|
| R4.1 | 打开项目 / 新建项目 / 切换项目任一动作前，若 `dirty === true`，先弹确认（保存 / 放弃 / 取消），取消则不执行打开 | P0 |
| R4.2 | 该 dirty 检查与关闭保护共用同一套判断与确认流程（复用，避免两套逻辑分叉） | P0 |
| R4.3 | 打开新项目成功前，若用户选「保存」，先完成保存再加载新项目 | P0 |

#### 功能 5 · 最小撤销/重做（P0）

| ID | 需求 | 优先级 |
|---|---|---|
| R5.1 | 界定「最小」可撤销范围 = 三类：节点增删、连线增删、节点属性/参数修改（改 prompt/模型/比例/分辨率/标题等） | P0 |
| R5.2 | 撤销/重做有深度上限（默认 50 步，超出丢弃最旧），深度值由架构师定 | P0 |
| R5.3 | 撤销/重做后 `dirty` 正确更新：撤销回到与磁盘一致状态时 `dirty` 复位为 false | P0 |
| R5.4 | 入口：键盘 `Ctrl+Z` / `Ctrl+Shift+Z`（或 `Ctrl+Y`）+ 顶栏按钮；无可撤销/重做时按钮灰显禁用 | P0 |
| R5.5 | 运行中（生成中）的节点状态变更不入撤销栈，避免撤销正在跑的任务；具体交互由架构师明确（见 Open Questions） | P0 |
| R5.6 | 节点位置拖动、视口平移/缩放是否纳入撤销栈（默认先不做，P1 再定） | P2 |

#### 功能 6 · 历史图库持久化（P0）

| ID | 需求 | 优先级 |
|---|---|---|
| R6.1 | 每次 AI 生成产出（image-gen / text-gen）追加写一行 trace 到项目目录 `history.jsonl`（每行一条 JSON） | P0 |
| R6.2 | trace 内容至少含：prompt、model、aspectRatio、resolution、count、refImageHashes、seed、createdAt、parentId、outputType（对齐方案 v3 §4.4） | P0 |
| R6.3 | 追加写采用单行 append（顺序写），保证多行不互相破坏；写失败不阻断生成结果展示，但需提示「历史记录未写入」 | P0 |
| R6.4 | 打开项目时能读取 `history.jsonl`，供历史图库跨会话展示 | P0 |
| R6.5 | 写入方（前端写 / 后端写）与 trace 和节点 `trace` 字段的关系（谁是 source of truth）由架构师拍板（见 Open Questions） | P0 |
| R6.6 | 旧 `.icproj` 打开后，历史图库为空时显示引导文案，不报错 | P1 |

### UI Design Draft（原生 DOM，非 React）

1. **关闭保护弹窗**（模态）：标题「有未保存的改动」；正文说明「当前项目有尚未保存的修改」；三按钮：`保存并关闭`（主）、`不保存`（次，危险色）、`取消`（弱）。焦点默认落在「保存并关闭」。Esc 等同「取消」。
2. **打开/切换前确认弹窗**（模态）：与关闭保护同款三按钮（`保存` / `放弃改动` / `取消`），仅标题文案换成「打开项目前有未保存的改动」。
3. **保存状态指示**（顶栏 `项目名 · 保存状态` 区域）：三态——`已保存 ✓`（灰/绿）/ `未保存 ●`（醒目，提示有改动）/ `保存中…`（弱）。自动保存发生时状态在 `未保存 → 保存中 → 已保存` 间静默流转，不弹 toast。
4. **撤销/重做入口**（顶栏）：两个按钮（撤销箭头 / 重做箭头），无可操作时灰显；同时支持 `Ctrl+Z`、`Ctrl+Shift+Z`（或 `Ctrl+Y`）。无需专用面板。
5. **历史图库**（左侧）：本次仅要求「能读到 history.jsonl 并展示」；trace 详情面板（「档案」按钮）沿用现有指令面板的「档案」入口，不在本次新造 UI。
6. **无额外自动保存 UI**：自动保存完全静默，只通过保存状态指示体现。

### Open Questions（架构师在设计时拍板或作假设）

1. **撤销/重做精确边界**：「最小」是否严格 = 节点增删 + 连线增删 + 属性/参数修改三类？节点位置拖动、视口平移缩放是否纳入？深度上限定多少（建议 50）？
2. **撤销与自动保存/快照的共存模型**：撤销/重做是「内存命令栈」还是「snapshots 快照回滚」？自动保存是否会固化历史使撤销失效？撤销回到与磁盘一致时 `dirty` 如何精确复位（需要脏状态与撤销栈联动机制）？
3. **自动保存与原子保存的关系**：自动保存是否复用 R1 的同一后端原子落盘路径？60 秒定时器与失焦触发如何避免与手动保存并发写同一文件？
4. **history.jsonl 写入方**：由前端（TS）还是后端（Python）负责写？单行 append 的并发/原子性如何保证？节点内 `trace` 字段与 history.jsonl 谁是 source of truth、是否需双向同步？
5. **新项目无路径时的落盘策略**：自动保存触发了但项目还没保存过路径，往哪写？关闭保护选「保存并关闭」但无路径，是否强制弹「另存为」对话框？
6. **运行中（生成中）的相互作用**：运行中是否允许撤销/自动保存/关闭？关闭时若有任务在跑，是提示中断还是拒绝关闭？（涉及 run-engine / poller 现有逻辑）
7. **`.tmp` 文件命名与清理**：同目录 `.tmp` 的命名约定？崩溃遗留 `.tmp` 的启动清理与识别规则？
8. **snapshots/ 快照是否属本步范围**：方案 v3 §八 布局含 `snapshots/`，但第 1 步 6 项未列「快照」。快照与撤销/重做的关系、以及是否在本步先做「崩溃恢复快照」的占位，请架构师界定。

## 四、验收标准

### 摘自方案 v3「十、验收标准」（与信任层直接相关）

| # | 原文 | 对应功能 |
|---|---|---|
| 1 | 打开软件 10 秒内能接着昨天的项目继续 | 自动保存 + 持久化（含 history.jsonl 跨会话读取） |
| 2 | 误关窗口不丢工作；崩溃最多丢一分钟 | 关闭保护 + 原子保存 + 自动保存 |
| 3 | 每张 AI 图都能查到它怎么来的 | 历史图库持久化（trace → history.jsonl） |

### 各功能可测验收点（补充）

**原子保存**
- AC-A1：写入过程中（如磁盘满/被杀进程）目标项目文件不损坏，仍是上一份完整内容。
- AC-A2：保存成功后目录内无残留 `.tmp` 文件；失败后 `.tmp` 被清理且原文件不变。

**自动保存**
- AC-A3：改动后 60 秒内无手动保存，系统自动落盘，`dirty` 复位，顶栏显示「已保存」。
- AC-A4：窗口失焦后，未保存改动被保存。
- AC-A5：无改动时不产生写盘（不频繁写文件）。

**关闭保护**
- AC-A6：有未保存改动时关窗口，弹三选一确认；选「取消」窗口不关。
- AC-A7：选「保存并关闭」→ 保存成功后关闭；保存失败不关闭并提示。
- AC-A8：无未保存改动时关窗口，不弹窗直接关闭。

**打开前 dirty 检查**
- AC-A9：有未保存改动时执行打开/新建/切换，先弹确认；选「取消」不执行打开，当前项目保持不变。
- AC-A10：选「保存」先落盘再加载新项目，新项目内容完整、无交叉污染。

**最小撤销/重做**
- AC-A11：删除节点 → `Ctrl+Z` 恢复节点及其连线；`Ctrl+Shift+Z` 再删回。
- AC-A12：修改参数后撤销，参数回到改前值，且 `dirty` 状态正确。
- AC-A13：连续撤销到已保存状态时 `dirty` 复位为 false，顶栏「已保存」；无可撤销时按钮灰显。

**历史图库持久化**
- AC-A14：执行一次生成后，`history.jsonl` 末尾新增一行合法 JSON trace，字段含 prompt/model/aspectRatio/resolution/refImageHashes/seed/createdAt/parentId/outputType。
- AC-A15：关闭并重开项目后，历史图库仍能列出该次生成记录。
- AC-A16：`history.jsonl` 写入失败时，生成结果仍正常展示，且有「历史未写入」的提示。

## 五、回传摘要

- **P0/P1/P2 分级结论**：6 项功能全部为 P0（信任地基，缺一不可）；P1 为运行中关闭行为（R3.4）、`history.jsonl` 空库引导（R6.6）、`.tmp` 启动清理（R1.4）；P2 为历史版本备份（R1.5）、自动保存间隔可配置（R2.6）、位置/视口撤销（R5.6）。
- **关键 Open Questions**（8 条）：见「三、Open Questions」——最重要的是撤销与自动保存/快照的共存模型（Q2）、history.jsonl 写入方与 trace 关系（Q4）、新项目无路径落盘策略（Q5）。
- **验收标准条目数**：摘取方案 v3 3 条（#1/#2/#3）+ 补充可测验收点 16 条（AC-A1 ~ AC-A16），共 **19 条**。

**对架构师最关键的一个决策点**：撤销/重做的实现模型——是「内存命令栈」还是「snapshots 快照回滚」——直接决定它如何与自动保存、`dirty` 复位、以及 `snapshots/` 目录共存，是本次设计里牵一发动全身的枢纽。
