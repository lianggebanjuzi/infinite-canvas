## 3. 共享契约落点（4.0 总控 §3 逐条核对）

### 3.1 媒体任务状态机（§3.2）

现状：
- **图片生成**：`run-engine` → `batch-queue`（JobStatus：queued/creating/running/succeeded/failed/cancelled）→ `poller.ts`（pending/done/not_found）——已经是「创建本地任务 → accepted(remote_task_id) → 轮询同一任务 → succeeded/failed」，符合“受理后不重投”。
- **视频**：`video-poller.ts` + `run-engine.runVideoGen`——创建本地 task → 拿到 remote_task_id → 轮询 → succeeded/failed/uncertain；查询错误显示“查询恢复中”，不换 Key 重投。✅ 但状态粒度粗：前端只有 `queued/run/stale/fail`，没有 `submitting/accepted/processing` 的细分展示。
- **图片编辑（mask/angle）**：`image-edit-engine.ts` 里已写 `imageEditTask { state: queued→submitting→accepted→queued/processing→… }` 与 `recover()`（查询恢复），**但未接线且 NodeStatus 类型里没有 `'submitting'`**（这也是 typecheck 报错原因之一）。
- **音频**：无。

结论与缺口：
1. **类型层**：`NodeStatus` 没有 `'submitting'`；`Partial<FlowNode>` 不接受。需要把媒体任务状态机从“节点状态”中独立出来（推荐：新建 `src/v1/engine/media-task.ts`，统一管理 image-edit/video/audio 的 `{state: queued|submitting|accepted|processing|succeeded|failed|cancelled|uncertain, localTaskId, remoteTaskId, error}`，并让 `imageEditTask`/`video.remoteTaskId`/audio 共用同一模型）。
2. **错误语义**：`poller.ts`/`video-poller.ts` 已把“查询错误”与“任务失败”区分开，但**图片编辑死代码没有 UI 展示**；4.2-C 历史/资产展示也需要这些状态字段。
3. **取消语义**：视频/图片编辑无「用户取消后远端任务标记 cancelled」的显式路径（只有本地放弃），按 4.0 §3.2 要求“用户能看到排队/已提交/查询恢复中/远端失败的区别”，需要状态展示面板（`status-visuals.ts`/`task-panel.ts` 目前只展示图片批次）。

## 5. 风险与待决

### R1（高，先决）typecheck 基线失败
