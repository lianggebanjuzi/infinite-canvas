# Infinite Canvas 3.1 架构蓝图与迁移路线

> 状态：实施中（第一阶段：媒体任务域）  
> 基线：`e325495`（2026-08-30）  
> 目标：在不改变桌面版交互、项目文件兼容性或供应商协议的前提下，把项目演进为可持续扩展的模块化单体。

---

## 1. 架构结论

本项目采用 **模块化单体（modular monolith）+ 应用用例 + 可替换基础设施适配器**。

- 保持单一桌面应用、单一 Python 后端进程和本地文件存储；不拆微服务。
- 按业务能力划分模块，而不是继续只按 `ui/`、`engine/`、`api/` 这类技术目录增长。
- 前端界面经由应用用例调用业务能力；不得直接拼供应商请求或操作底层 pywebview 对象。
- 后端把供应商协议、文件系统、桌面对话框视为可替换的基础设施适配器。
- 先保留现有公开 API 和项目文件格式，通过兼容门面逐步迁移；每一阶段都可独立回滚。

这不是一次重写。当前画布、节点、生成、项目、备份和导演台功能均继续运行；重构只改变内部责任归属。

## 2. 当前基线与主要风险

当前代码已有明确的前后端分层，也已有画布、生成、资产、项目、供应商和导演台等功能模块。问题主要是跨模块协调器过大：

| 文件 | 当前规模 | 风险 |
|---|---:|---|
| `backend/api/unified_api.py` | 2407 行 | 路由、协议适配、任务、下载和错误语义混合 |
| `src/v1/engine/run-engine.ts` | 1478 行 | 多种媒体执行、轮询、节点写回、批处理混合 |
| `src/v1/ui/settings-panel.ts` | 1785 行 | 设置、供应商、模型、能力配置混合 |
| `src/v1/ui/cmd-panel.ts` | 1428 行 | 节点创建、编辑、资源插入与执行入口混合 |
| `main.py` | 976 行 | 应用启动、依赖装配和 pywebview API 门面混合 |

最先处理媒体任务域，因为图片编辑、视频和音频都存在“提交后只能查询原任务、不得自动重投”的共同业务规则；这类规则分散时最容易引入重复扣费和恢复不一致。

## 3. 目标结构

目标结构是业务分层，而不是强制一次性迁移所有文件：

```text
src/
  app/                         # 启动、装配、桌面平台入口
  contracts/                   # 前后端稳定请求/响应契约
  shared/                      # 通用错误、事件、纯工具、基础 UI
  features/
    workflow/                  # 节点、连线、选择、撤销、画布状态
    generation/                # 媒体任务、执行器、轮询、结果落盘用例
    assets/                    # 多媒体资产、引用、缩略图、溯源
    projects/                  # 项目、历史、工作流、备份、资源包
    providers/                 # 供应商、模型目录、能力 schema
    image-editing/             # 裁剪、切图、蒙版、标注、多角度、扩图
    director/                  # 导演台入口和主画布互通
  ui/
    components/                # 不含业务规则的通用控件
    shell/                     # 顶层布局、抽屉、快捷键

backend/
  app/                         # 启动与依赖装配
  contracts/                   # pywebview API 的稳定契约说明
  modules/
    generation/                # 任务、路由、适配器
    providers/                 # Provider 配置、模型和能力
    projects/                  # 项目/历史/资产索引
    media/                     # 文件准备、下载、元数据、临时文件
    bundles/                   # .icbundle 与 .icbackup
    director/                  # 导演台项目、窗口和导入导出
  infrastructure/              # HTTP、文件系统、对话框、系统集成
  shared/                      # 错误、原子 IO、公共校验
```

现阶段不移动目录；新增代码先遵循此结构，旧代码在相邻的迁移切片中逐步收敛。

## 4. 依赖方向

```text
UI / Desktop Window
        ↓
Application Use Cases
        ↓
Domain State and Rules
        ↓
Ports (contracts/interfaces)
        ↓
Adapters (pywebview, filesystem, OpenAI, Gemini, FluxPort)
```

必须遵守的规则：

1. `ui/` 不得直接调用 `window.pywebview.api`；只经由前端 API 门面或应用用例。
2. `workflow` 只管理图结构与编辑状态，不知道 API Key、供应商协议或 DOM。
3. `generation` 拥有任务状态与恢复规则，不把轮询和重试规则散落给 UI。
4. `providers` 只管理路由与能力，不感知节点卡片、画布坐标或项目 UI。
5. `projects` 拥有文件格式与持久化；项目数据不得包含密钥或账户信息。
6. `director` 通过项目/资产契约与画布互通，不直接读写主画布单例。
7. 后端 `main.py` 只做依赖装配和 pywebview 门面；新业务逻辑进入对应模块。

## 5. 业务模块与数据归属

| 模块 | 负责 | 不负责 |
|---|---|---|
| Workflow | 节点、端口、连线、选择、撤销、画布布局 | 生成协议、项目文件 IO |
| Generation | 创建任务、状态迁移、轮询、取消、恢复、结果写回 | UI 弹层和供应商配置编辑 |
| Assets | 图片/视频/音频资产、标签、缩略图、来源追溯、引用 | 上游 API 请求细节 |
| Projects | `.icproj`、历史、工作流、资源包、备份 | API Key 与账户凭据 |
| Providers | Provider、Key、模型目录、能力 schema、适配器选择 | 画布节点和 DOM |
| Director | 场景、镜头、人物、时间轴、`.icdirector` | 主画布内部状态对象 |

数据归属：

```text
应用级（不可随项目导出）
  providers_data.json / settings.json / prompts_library.json /
  capability_schemas.json

项目级（可移动、可备份、可导出）
  *.icproj / assets.json / history.jsonl / 项目媒体目录 /
  *.icdirector / *.icbundle
```

项目内保存模型标识、能力快照、生成参数、来源和远端任务 ID；绝不保存 API Key。

## 6. 统一媒体任务契约

所有异步媒体任务使用同一状态语义：

```text
queued → submitting → accepted → processing
      → succeeded | failed | cancelled | uncertain
```

- `accepted` 代表后端已经拿到本地任务 ID，若上游返回远端 ID 则一并记录。
- 进入 `accepted` 后，任何网络异常只能进入 `uncertain` 或继续查询；禁止自动换 Key 或重新提交。
- `uncertain` 是可恢复状态，不是失败的同义词。
- 节点展示状态可以保持现有 `queued/run/done/fail/stale`，由任务状态映射，避免影响现有卡片和持久化兼容性。
- 初期覆盖视频、音频和图片编辑；批量图片生成仍保持现有批次队列，后续在兼容后接入。

## 7. 前后端契约策略

pywebview 仍是当前唯一桌面通信方式。需要收敛的是其使用面，而不是改成 HTTP：

```text
DesktopApi
  providers.*
  generation.images.*
  generation.videos.*
  generation.audio.*
  projects.*
  assets.*
  bundles.*
  director.*
```

当前 `src/utils/api.ts` 的方法继续保留兼容。后续按域增加命名空间门面；只有该门面知道 pywebview 的具体函数名。这样未来切换 Web、Tauri/Electron 或云端服务时，业务代码只替换适配器。

## 8. 导演台的长期边界

导演台是独立入口和独立项目格式，不是画布的一个大型 UI 面板。与主画布仅通过两个用例协作：

```text
OpenDirector({ sourceAsset, sourceProject, sourceNode })
ImportDirectorOutput({ asset, provenance, trace })
```

这允许未来将导演台迁移为独立发布物、增加云渲染或替换 Three.js 实现，而不破坏工作流画布。

## 9. 迁移路线

### 阶段 A：架构护栏（本文件）

- 固化模块边界、数据归属和依赖规则。
- 保持当前目录与 API 不变。
- 每个后续切片都以类型检查与针对性 smoke 测试作为验收条件。

### 阶段 B：媒体任务域（当前实施）

- 新建无 UI 依赖的 `media-task` 状态映射工具。
- 让视频与音频的状态归一和恢复逻辑优先共用该工具。
- 保留 `runEngine`、节点参数字段和轮询接口，不改变行为。
- 后续把图片编辑接入相同状态契约。

### 阶段 C：资产与项目域

- `ImageAssetRecord` 演进为 `AssetRecord`，统一 image/video/audio/director-output。
- 收敛资产抽屉、历史抽屉、导入导出对资产索引的访问。
- 为所有资产建立稳定 `assetId` 和 `provenance`。

### 阶段 D：供应商与适配器域

- 分离 Provider 配置、模型目录、能力 schema、请求适配器。
- 新供应商通过 adapter + schema + 映射测试接入，不修改画布流程。

### 阶段 E：UI 协调器拆分

- `settings-panel` 拆为 Provider、Model、Schema、Preference 面板。
- `cmd-panel` 拆为节点创建、节点检查器、资源引用。
- `main.ts` 收敛为应用启动和全局快捷键装配。

### 阶段 F：平台与协作（不提前实现）

- Web/Tauri/Electron 适配器、云同步、多人协作、插件市场、后台长任务。
- 只有在实际产品需求明确后才实现；当前仅由稳定 contracts 和模块边界为其留出空间。

## 10. 第一切片的验收标准

1. 视频和音频任务的状态映射不再由 `run-engine.ts` 私有实现。
2. 恢复查询仍只使用已持久化的 local/remote task ID，不重新提交任务。
3. 节点的现有字段、状态名称和 UI 表现不变。
4. `npm run typecheck` 与 Python 后端编译通过。
5. 至少运行已有音频和导演台相关 smoke 测试，确认改造未波及已有路径。
