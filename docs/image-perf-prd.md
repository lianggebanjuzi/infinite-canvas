# PRD：图片性能优化 + 多 Key 前端合并展示

## 1. 项目信息

- **Language**: 中文
- **技术栈**: pywebview + TypeScript/Vite（沿用现有）
- **Project Name**: image_perf_and_key_merge
- **原始需求**：
  1. **图片性能**：4K 生成图以 base64 data URL 直接渲染，单张 30-80MB，两张即卡；希望画布放几十~上百张 4K 图不卡。
  2. **多 Key 前端合并**：刚上线的多 Key 在节点模型列表暴露 key 名（label 带 key）、设置面板每 key 独立卡片，用户反馈「前端没必要暴露 key，后端区分开就好」。后端 keys[] 结构**不动**，只改前端展示层。

## 2. 产品定义

### 产品目标（一句话）
让画布流畅承载几十~上百张 4K 图（前端只持有缩略图、大图按需加载），同时把多 Key 概念完全收敛到后端，前端节点选模型只见「供应商 · 模型名」不见 Key。

### 用户故事
1. 作为电商视觉设计师，我希望画布上铺开几十上百张 4K 生成图依然流畅滚动/缩放，这样我能一次对比整批概念稿，不被卡死。
2. 作为用户，我希望点卡片「查看大图」时才加载原图、平时画布只显示缩略图，这样平时保持轻量、需要细节时再花资源。
3. 作为用户，我希望节点模型列表只显示「供应商 · 模型名」、不出现任何 Key 概念，这样选模型和以前一样简单，我不关心后端分了几组 Key。
4. 作为用户，我希望设置里仍能为同一供应商添加/填写多个 Key 并各自拉取模型，这样我依然能用第二个 Key 的分组模型，只是日常出图不用管它。

## 3. 需求池

### P0（本期必须）
**图片性能**
- P0-1 后端主生成链路（generate_image_async / _save_images_to_local 路径）**原图落盘 + 生成缩略图**（最长边 ~1024px，JPEG/WebP，几十 KB），返回结构新增缩略图字段。
- P0-2 前端卡片主视觉改用**缩略图**（node 存展示用小图），前端不再常驻原图 base64。
- P0-3 「查看大图」**按需加载原图**：点击时才取，加载中给 loading 态，失败回退缩略图放大并提示。
- P0-4 历史图库 / 资产库**同步用缩略图**（新生成图写缩略图引用，拖入画布/复现/采纳/锁定沿用现有交互）。

**多 Key 前端合并**
- P0-5 节点模型列表（fetchImageModels / fetchChatModels / 默认模型下拉）**合并展示所有 enabled key 的模型**：label 简化为「供应商短名 - 模型名」，**不带 key 名**；id 仍三段式（后端路由零改动）。
- P0-6 跨 key 重名模型**去重**：同供应商同名模型只出现一次，路由到第一个可用 key（消歧策略见待确认 4）。
- P0-7 设置面板**保留多 Key 填写能力**（可添加第二个 Key、各自拉取模型），但 Key 文案弱化（如「密钥组」/高级折叠），不干扰常规使用。

> **本期 P0 范围**：出图链路缩略图化 + 前端卡片/大图/图库资产全部只持小图 + 节点/默认模型列表隐藏 key 概念。后端 keys[] 数据结构与三段解析**不改**；旧项目/旧 history 无缩略图时回退原图（仅旧数据变慢，不阻断）。

### P1（应该，可后置）
- 缩略图尺寸/质量可配置（settings 加 thumbnail_max_size / quality）。
- 大图弹窗 loading/失败/缺失提示完善；原图路径缺失时优雅回退。
- 旧数据兼容增强：为存量 history/资产批量补缩略图（懒迁移，打开时按需生成）。

### P2（可以后置）
- 缩略图磁盘缓存/去重（同图不重复生成）。
- 卡片视口外懒加载（IntersectionObserver 延迟渲染）。
- 历史图库/资产库虚拟滚动或分批渲染优化（现有分批渲染已部分覆盖）。

## 4. 数据/接口约束（给架构师）

### 4.1 缩略图怎么传
- **建议**：生成任务结果新增 `thumbnail`（单图）/ `thumbnails`（多图），与现有 `image_url` / `images` **并列返回**；`thumbnail` 为缩略图 base64 data URL（几十 KB，前端直接可渲染）。
- 前端 `node.imageUrl` 语义切换为**展示用缩略图**；新增 `node.originalUrl`（或 `imageOrigin`）存原图引用（`file:///` 本地路径或后端读取句柄），**仅查看大图时使用**。
- 历史/资产索引（history.jsonl / assets）新记录写缩略图引用；旧记录无缩略图字段时回退现有 base64 原图。

### 4.2 原图怎么取
- 后端已有现成通道：`load_local_image(file_path)`（返回 base64 data_url）、`save_image_to_local`（返回 `file:///url` + `thumbnail`），可作为按需取原图通道，优先复用。
- **待确认**：pywebview 前端能否直接 `<img src="file:///...">` 直读本地路径（受 webview 安全策略限制）；若不可行，统一走 `load_local_image` 桥接按需加载（大图一次性 base64 载入，用完即弃，不常驻）。
- **不建议**为原图新增后端 HTTP 静态服务（扩大攻击面、改动大）；除非 file:// 直读被禁且桥接不可接受。

### 4.3 模型合并后 label/id 语义
- **id 保持三段式** `${providerId}:${keyId}:${modelId}` 不变 —— 后端 `_resolve_drawing_model` / `_resolve_chat_model`、存量节点、localStorage 默认模型全部零改动。
- **label 简化**：`${供应商短名} - ${模型名}`（去掉 key 名），`fetchImageModels` / `fetchChatModels` / 设置面板默认模型下拉统一。
- **重名去重**：同供应商跨 key 同名模型只保留**第一个可用 key** 的条目（id 路由到该 key）；仅当确有歧义场景（待确认 4）才追加最小消歧后缀。
- 设置面板是**唯一**仍可见 key 概念的面：key 卡片（添加/密钥/拉取模型/启停/删除）保留，但模型管理区与默认下拉的 label 同步简化。

## 5. 待确认问题

1. **缩略图格式与尺寸**：JPEG q85 / 最长边 1024px 是否 OK？还是 WebP（体积更小，但 pywebview 渲染兼容性需验证）？
2. **原图访问方式**：pywebview `<img src="file:///">` 直读可行吗？不可行则统一 `load_local_image` 桥接按需加载 —— 需拍板。
3. **生成结果是否默认不再回传原图 base64**：只传缩略图可彻底解决内存问题；但旧依赖（history entry.imageUrl 存 base64、项目文件存 base64）是否接受「新图缩略图+路径引用、旧图仍 base64」双轨？
4. **跨 key 重名模型策略**：默认只留第一个可用 key；若用户需要选第二个 key 的同名模型（不同额度/分组），是否提供折叠的「密钥组」小字标注，还是本期一律隐藏 key？
5. **设置面板 key 文案弱化程度**：完全折叠（高级区）还是改称「密钥组」即可？节点路径不出现 key 为本期硬约束。
